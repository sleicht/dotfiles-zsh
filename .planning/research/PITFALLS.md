# Pitfalls Research

**Domain:** Adding mise task runner to existing chezmoi-managed dotfiles
**Researched:** 2026-02-14
**Confidence:** HIGH

## Critical Pitfalls

### Pitfall 1: Shell Startup Performance Regression

**What goes wrong:**
Adding mise tasks integration causes shell startup time to exceed the 139.8ms baseline, potentially adding 60-80ms overhead from mise activation and task file loading. Current shell startup is 77.2ms (measured), which is excellent, but mise task files loaded unconditionally on every shell init can push this past 150ms.

**Why it happens:**
Mise's `mise activate` hook runs on every shell prompt (precmd) unless configured to only run on directory changes (chpwd). Task files are scanned and loaded even when not being executed. Developers add `mise activate` to `.zshrc` without understanding the performance implications or optimising the activation mode.

**How to avoid:**
1. Configure mise to only check on directory changes: mise's built-in optimisation exits early if directory wasn't changed or config files haven't been modified
2. Avoid defining tasks in `mise.toml` if not needed — prefer file tasks in `.mise/tasks/` which are only loaded on-demand
3. Use `mise activate --no-hook-env` and call `mise hook-env` manually only when needed
4. Consider using `mise exec` or `mise run` instead of shell activation for task-heavy workflows
5. Measure before/after with `hyperfine --warmup 1 --runs 5 "zsh -i -c exit"`

**Warning signs:**
- Shell feels sluggish when opening new terminals or changing directories
- `zprof` output shows mise activation taking >50ms
- Task files are being parsed on every shell init (check with `mise --trace`)
- `mise doctor` shows many task files or complex mise.toml

**Phase to address:**
Phase 1 (Foundation) — establish performance baseline and measurement strategy before any mise task integration

**Sources:**
- [Shell startup overhead discussion](https://github.com/jdx/mise/discussions/6279) — up to 80ms overhead reported
- [Optimising ZSH init with mise](https://www.mikekasberg.com/blog/2025/05/29/optimizing-zsh-init-with-zprof.html)
- [Mise activation documentation](https://mise.jdx.dev/cli/activate.html)

### Pitfall 2: Chezmoi Template Execution vs Mise Task Execution Confusion

**What goes wrong:**
Overlap and confusion between chezmoi's `run_once_` / `run_onchange_` scripts and mise tasks leads to duplicate operations, unclear ownership, and race conditions. For example, both chezmoi and mise might try to install dependencies, generate completions, or update configurations, causing idempotency failures and unpredictable behaviour.

**Why it happens:**
Both tools solve similar problems (automation, lifecycle hooks) but with different semantics:
- Chezmoi: runs scripts during `chezmoi apply` based on content hash changes
- Mise: runs tasks on-demand via `mise run` or as dependencies of other tasks

Developers naturally try to use both for similar purposes without establishing clear boundaries. Chezmoi scripts can call `mise run`, creating circular dependencies. Mise tasks might assume chezmoi state that hasn't been applied yet.

**How to avoid:**
1. **Establish clear ownership boundaries:**
   - Chezmoi scripts: bootstrap (install homebrew, mise itself, age keys), one-time system setup, dotfile deployment lifecycle
   - Mise tasks: development workflows (build, test, lint), dotfile operations (update, validate), repeatable operations

2. **Never call `mise run` from chezmoi `run_once_` scripts** — creates timing dependencies and defeats idempotency

3. **Use naming convention:**
   - Chezmoi scripts: `run_once_before_XX-action.sh` (bootstrap/setup)
   - Mise tasks: `dotfiles:action`, `dev:action` (repeatable workflows)

4. **Document in CLAUDE.md which tool owns which operations**

**Warning signs:**
- Operations run twice (completions generated by both chezmoi and mise)
- `chezmoi apply` behaviour differs based on whether mise tasks have been run
- Circular dependency errors
- Scripts fail because mise tasks haven't run, or vice versa
- Different results from `chezmoi apply` vs `mise run dotfiles:apply`

**Phase to address:**
Phase 1 (Foundation) — define clear boundaries and ownership model before implementing any tasks

**Sources:**
- [Chezmoi run scripts documentation](https://www.chezmoi.io/user-guide/use-scripts-to-perform-actions/)
- [Chezmoi + mise integration article](https://manuelchichi.com.ar/blog/personal-toolset-2025/)
- [Chezmoi run_once_ discussion](https://github.com/twpayne/chezmoi/discussions/1678)

### Pitfall 3: Task File Permissions After Chezmoi Apply

**What goes wrong:**
Task files in `.mise/tasks/` lose executable permissions after `chezmoi apply`, causing "Permission denied" errors when running tasks. Mise requires task files to be executable to detect and run them, but chezmoi's default file permissions are 0o644 (non-executable).

**Why it happens:**
Chezmoi manages task files as regular files unless explicitly marked with the `executable_` attribute. The directory structure in chezmoi source would be:

```
.local/share/chezmoi/
  private_dot_mise/
    tasks/
      executable_update-dotfiles  # Needs executable_ prefix
```

Without `executable_`, chezmoi applies the file with 0o644, and mise ignores it. This is easy to miss because the file might work in the source directory (if you made it executable there) but fails after deployment.

**How to avoid:**
1. **Always use `executable_` prefix for task files:**
   ```
   .local/share/chezmoi/private_dot_mise/tasks/executable_task-name
   ```

2. **Use `exact_` prefix on tasks directory to let chezmoi manage deletions:**
   ```
   .local/share/chezmoi/private_dot_mise/exact_tasks/
   ```

3. **Verify after `chezmoi apply`:**
   ```bash
   ls -la ~/.mise/tasks/
   mise tasks  # Should list all tasks
   ```

4. **Add to mise task validation:**
   ```toml
   [tasks.validate-tasks]
   run = '''
   for task in ~/.mise/tasks/*; do
     if [[ ! -x "$task" ]]; then
       echo "ERROR: $task is not executable"
       exit 1
     fi
   done
   '''
   ```

**Warning signs:**
- `mise tasks` returns empty or incomplete list after `chezmoi apply`
- "No such file or directory" errors when running `mise run task-name`
- Tasks work in development but fail after deployment
- `ls -la ~/.mise/tasks/` shows `-rw-r--r--` instead of `-rwxr-xr-x`

**Phase to address:**
Phase 2 (Task File Structure) — establish correct file permissions during initial task file setup

**Sources:**
- [Chezmoi executable files](https://www.chezmoi.io/user-guide/manage-different-types-of-file/)
- [Chezmoi target types](https://www.chezmoi.io/reference/target-types/)
- [Mise file tasks](https://mise.jdx.dev/tasks/file-tasks.html) — requires executable files

### Pitfall 4: Task Path Resolution and Working Directory Confusion

**What goes wrong:**
Tasks fail with "file not found" or operate in the wrong directory because mise's working directory behaviour differs from expectations. Mise sets the current working directory to the directory of `mise.toml` before running tasks, but developers expect the original invocation directory. Relative paths in task scripts break, sources/outputs become unreachable, and cross-project task calls fail.

**Why it happens:**
Mise changes the working directory to `config_root` (the directory containing mise.toml) before task execution. This is different from Make, npm scripts, or shell scripts which typically preserve the caller's working directory. The environment variables are:

- `MISE_ORIGINAL_CWD`: Where the task was invoked from
- `MISE_CONFIG_ROOT`: Where mise.toml lives (also the task's working directory)
- `MISE_TASK_DIR`: Where the task script file is located

Additionally, there's a known issue where task sources are relative to CWD, not config_root, which is inconsistent with other path directives.

**How to avoid:**
1. **Use absolute paths or environment variables:**
   ```bash
   # Wrong - assumes CWD
   ./scripts/build.sh

   # Right - uses config_root
   "${MISE_CONFIG_ROOT}/scripts/build.sh"
   ```

2. **Override working directory if needed:**
   ```toml
   [tasks.task-name]
   dir = "{{cwd}}"  # Run from original directory
   ```

3. **Document assumptions in task headers:**
   ```bash
   #!/bin/bash
   #MISE description="Updates dotfiles (runs from config root)"
   # Working directory: ${MISE_CONFIG_ROOT}
   # Task file location: ${MISE_TASK_DIR}
   ```

4. **Test tasks from different directories:**
   ```bash
   cd /tmp && mise run dotfiles:validate
   ```

**Warning signs:**
- Tasks work when run from `~/.dotfiles` but fail from other directories
- "No such file or directory" errors for scripts or resources
- Tasks can't find mise.toml or other config files
- Unexpected behaviour when calling tasks from task dependencies

**Phase to address:**
Phase 2 (Task File Structure) — establish path conventions and document working directory assumptions

**Sources:**
- [Mise task working directory](https://mise.jdx.dev/tasks/)
- [Task sources path issue](https://github.com/jdx/mise/discussions/4596)
- [Mise environment variables](https://mise.jdx.dev/environments/)

### Pitfall 5: Cross-Platform Incompatibility in Task Scripts

**What goes wrong:**
Tasks work on macOS but fail on Linux (or vice versa) due to different shell utilities, paths, or platform-specific commands. Tasks using `brew`, `pbcopy`, `open`, or macOS-specific paths break on Linux. GNU vs BSD differences in common commands (`sed`, `grep`, `find`) cause subtle failures.

**Why it happens:**
Dotfiles are typically developed on a single platform, and cross-platform differences only surface when deploying to a different OS. Common issues:

- Homebrew locations: `/opt/homebrew/bin` (macOS ARM) vs `/usr/local/bin` (macOS Intel) vs `/home/linuxbrew/.linuxbrew/bin` (Linux)
- Shell shebangs: `/bin/bash` may be bash 3.2 on macOS, bash 5.x on Linux
- Command availability: `pbcopy/pbpaste` (macOS), `xclip/xsel` (Linux)
- GNU vs BSD command flags: `sed -i` vs `sed -i ''`, `grep -P` (GNU only)

**How to avoid:**
1. **Use platform detection in tasks:**
   ```bash
   #!/usr/bin/env bash
   #MISE description="Cross-platform task"

   if [[ "$OSTYPE" == "darwin"* ]]; then
     # macOS
     brew bundle
   elif [[ "$OSTYPE" == "linux-gnu"* ]]; then
     # Linux
     sudo apt-get update
   fi
   ```

2. **Use portable shebangs:**
   ```bash
   #!/usr/bin/env bash  # Not #!/bin/bash
   ```

   According to 2025 surveys, `#!/usr/bin/env bash` is now the recommended approach for portability.

3. **Leverage chezmoi templates for platform-specific tasks:**
   ```
   .mise/tasks/
     executable_update-macos.tmpl
     executable_update-linux.tmpl
   ```

   In template:
   ```bash
   {{ if eq .chezmoi.os "darwin" -}}
   #!/usr/bin/env bash
   brew bundle
   {{ end -}}
   ```

4. **Document platform support:**
   ```toml
   [tasks.update]
   description = "Update system packages (macOS only)"
   ```

5. **Test on both platforms or use Docker:**
   ```bash
   docker run --rm -v ~/.dotfiles:/dotfiles ubuntu bash -c "cd /dotfiles && mise run validate"
   ```

**Warning signs:**
- Tasks succeed on development machine but fail in CI or on other machines
- "Command not found" errors on different platforms
- Different output or behaviour on macOS vs Linux
- Shebang errors or interpreter not found

**Phase to address:**
Phase 2 (Task File Structure) — establish cross-platform conventions early, test on target platforms

**Sources:**
- [Mise cross-platform development](https://betterstack.com/community/guides/scaling-nodejs/mise-explained/)
- [Bash shebang best practices 2025](https://www.techedubyte.com/bash-shebang-bin-bash-vs-usr-bin-env-bash-explained-3/)
- [Chezmoi OS detection](https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/)

### Pitfall 6: Secrets and Sensitive Data in Task Configurations

**What goes wrong:**
Sensitive data (API tokens, credentials, private paths) leaks into version control through mise.toml task definitions or task scripts. Task files that reference `.env` files, hardcode tokens, or expose machine-specific secrets get committed to the repository, creating security vulnerabilities.

**Why it happens:**
Developers naturally want to use environment variables in tasks for API access, deployment credentials, or private service URLs. Without proper separation, these end up in `mise.toml` (committed) instead of `mise.local.toml` (gitignored). Chezmoi templates might also expose secrets if not properly handled.

**How to avoid:**
1. **Use mise.local.toml for sensitive values:**
   ```toml
   # ~/.config/mise/config.toml (committed)
   [env]
   # Public env vars only

   # ~/.config/mise/config.local.toml (gitignored)
   [env]
   GITHUB_TOKEN = "ghp_xxx"
   OPENAI_API_KEY = "sk-xxx"
   ```

2. **Add to .chezmoiignore:**
   ```
   .config/mise/config.local.toml
   .mise.local.toml
   .mise.*.local.toml
   ```

3. **Use redactions for debugging:**
   ```toml
   [env]
   GITHUB_TOKEN.redact = true
   # Or use patterns
   redactions = ["SECRET_*", "*_TOKEN", "*_API_KEY"]
   ```

4. **In task files, source from separate env file:**
   ```bash
   #!/usr/bin/env bash
   #MISE description="Deploy (requires credentials)"

   # Don't hardcode secrets
   if [[ -f "$HOME/.config/mise/config.local.toml" ]]; then
     # mise loads this automatically
     deploy_app "$DEPLOY_TOKEN"
   else
     echo "ERROR: Missing config.local.toml with DEPLOY_TOKEN"
     exit 1
   fi
   ```

5. **Validate in CI that no secrets are committed:**
   ```bash
   # Check for common secret patterns
   gitleaks detect --no-git
   ```

**Warning signs:**
- Tokens or credentials visible in `git diff`
- Task files reference hardcoded paths like `/Users/username/`
- `.env` files or `.local.toml` files are tracked by git
- CI fails with "permission denied" but works locally
- Secrets exposed in mise task output or logs

**Phase to address:**
Phase 1 (Foundation) — establish secrets management pattern before creating any tasks with credentials

**Sources:**
- [Mise environment security best practices](https://combray.prose.sh/2025-11-26-mise-project-structure-env-vars)
- [Mise redactions](https://mise.jdx.dev/environments/)
- [Secure .env best practices](https://blog.gitguardian.com/secure-your-secrets-with-env/)

### Pitfall 7: Circular Task Dependencies and Deadlocks

**What goes wrong:**
Task dependency chains contain circular references causing mise to error with "Circular dependency detected: task-a → task-b → task-a". More subtle deadlocks occur with `wait_for` dependencies where parallel tasks wait on each other, causing hangs.

**Why it happens:**
As task systems grow, dependencies become complex:
```toml
[tasks.test]
depends = ["build"]

[tasks.build]
depends = ["lint"]

[tasks.lint]
depends = ["test"]  # Circular!
```

Or with `wait_for`:
```toml
[tasks.task-a]
wait_for = ["task-b"]

[tasks.task-b]
wait_for = ["task-a"]  # Deadlock!
```

Mise detects simple circular dependencies but subtle ones can slip through, especially across multiple mise.toml files or included task files.

**How to avoid:**
1. **Keep dependency graphs shallow and acyclic:**
   - Maximum 2-3 levels deep
   - Draw dependency diagrams for complex workflows

2. **Use `wait_for` instead of `depends` for loose coupling:**
   ```toml
   [tasks.deploy]
   depends = ["build"]      # Must run and succeed
   wait_for = ["test"]      # Only waits if test is in current execution
   ```

3. **Establish dependency direction conventions:**
   - Low-level → high-level (build → test → deploy)
   - Never reverse direction

4. **Validate dependency graph:**
   ```bash
   mise tasks tree  # Visualise task dependencies
   ```

5. **Test parallel execution:**
   ```bash
   mise run --jobs 4 task-a task-b task-c
   ```

**Warning signs:**
- "Circular dependency detected" errors from mise
- Tasks hang indefinitely with no output
- `mise run` never completes
- Task execution order is unpredictable
- Adding a new dependency breaks unrelated tasks

**Phase to address:**
Phase 3 (Basic Tasks) — establish dependency patterns early, validate before complexity grows

**Sources:**
- [Mise task dependency architecture](https://mise.jdx.dev/tasks/architecture.html)
- [Circular dependency detection](https://mise.jdx.dev/tasks/architecture.html) — mise detects and reports these
- [Task dependencies discussion](https://github.com/jdx/mise/discussions/3761)

### Pitfall 8: Task Name Collisions with Future Mise Commands

**What goes wrong:**
Tasks are named with short names like `run`, `install`, `update`, which work initially using the shorthand `mise <task>`. Later, mise adds a built-in command with the same name, and suddenly `mise run` executes the mise built-in instead of your task, breaking workflows and scripts.

**Why it happens:**
Mise allows running tasks with `mise <TASK>` if the name doesn't conflict with a mise command. The documentation warns: "Because mise may later add a command with a conflicting name, it's recommended to use `mise run <TASK>` in scripts and documentation." This is a real risk — mise is actively developed and new commands are added regularly.

**How to avoid:**
1. **Always use `mise run <TASK>` in scripts:**
   ```bash
   # Wrong - will break if mise adds an "install" command
   mise install

   # Right - always explicit
   mise run install
   ```

2. **Use namespaced task names:**
   ```toml
   [tasks."dotfiles:install"]  # Not [tasks.install]
   [tasks."dev:build"]         # Not [tasks.build]
   [tasks."test:unit"]         # Not [tasks.test]
   ```

3. **Avoid common verb names:**
   - Reserved/risky: `run`, `install`, `update`, `setup`, `config`, `env`, `version`, `list`, `add`, `remove`
   - Safer: `dotfiles:apply`, `dev:serve`, `project:init`

4. **Document task invocation format:**
   ```bash
   # In CLAUDE.md or README
   # Always use: mise run task-name
   # Never use: mise task-name
   ```

**Warning signs:**
- Tasks that worked before suddenly behave differently
- `mise <task>` shows mise help instead of running your task
- Scripts fail after mise upgrade
- Task not found errors after previously working

**Phase to address:**
Phase 2 (Task File Structure) — establish naming conventions before creating tasks

**Sources:**
- [Mise running tasks documentation](https://mise.jdx.dev/tasks/running-tasks.html) — explicit warning about future conflicts
- [Mise CLI reference](https://mise.jdx.dev/cli/run.html)

## Technical Debt Patterns

Shortcuts that seem reasonable but create long-term problems.

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Defining all tasks in `mise.toml` instead of separate files | Single file, easy to edit | Slower shell startup, harder to test individual tasks, complex TOML escaping | Only for 1-3 trivial tasks |
| Using `set +e` to ignore errors in tasks | Tasks complete even with failures | Silent failures, broken deployments, hard to debug | Never — use proper error handling and recovery |
| Hardcoding paths instead of using `${MISE_CONFIG_ROOT}` | Works on your machine | Breaks on other machines, CI, or different directory structures | Never — always use config_root or absolute paths |
| Skipping task documentation (`#MISE description=`) | Faster to write | Unclear purpose, hard to discover tasks, poor `mise tasks` output | Never — documentation is mandatory |
| Not testing tasks on target platforms | Faster development | Platform-specific failures in production | Only if platform is documented and validated in CI |
| Using `mise activate` without performance measurement | Easy setup | Unknown performance impact, potential shell lag | Never — always measure before/after |
| Mixing chezmoi and mise for the same operations | Flexibility, can use either | Duplication, race conditions, unclear ownership | Never — establish clear boundaries |

## Integration Gotchas

Common mistakes when connecting mise tasks with other tools.

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| Chezmoi scripts | Calling `mise run` from `run_once_` scripts | Establish clear boundaries: chezmoi for bootstrap, mise for workflows |
| Homebrew | Running `brew bundle` in both chezmoi and mise | Use chezmoi `run_once_` for initial install, mise task for updates |
| Git hooks | Installing git hooks via mise tasks | Use chezmoi for hook installation, mise tasks for hook execution logic |
| Shell completions | Generating in both `run_once_` and mise task | Use chezmoi `run_once_after_` for initial generation, mise task for regeneration |
| Environment variables | Storing same vars in both chezmoi templates and mise.toml | Single source of truth: mise.toml for runtime env, chezmoi templates for static config |
| Secrets | Committing mise.toml with sensitive data | Always use mise.local.toml (gitignored) for secrets, mise.toml for public config |

## Performance Traps

Patterns that work at small scale but fail as usage grows.

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Scanning all task files on shell init | Shell startup gets slower over time | Use file tasks in `.mise/tasks/`, not TOML tasks; configure mise to only check on chpwd | >10 task files or complex mise.toml |
| Complex task dependencies | Tasks take longer to start, `mise run` is slow | Keep dependency graphs shallow, use `wait_for` for loose coupling | >3 levels of dependencies |
| Large task outputs to stdout | Terminal becomes slow, logs fill disk | Use `task_output = "quiet"` or redirect to files | Tasks producing >10MB output |
| Running heavy tasks in `depends_post` | Tasks appear to hang after completion | Only use `depends_post` for lightweight cleanup/notifications | `depends_post` tasks take >5 seconds |
| Task scripts without proper error handling | Failures cascade, hard to debug | Always use `set -e`, validate inputs, provide clear error messages | Any production task |

## Security Mistakes

Domain-specific security issues beyond general web security.

| Mistake | Risk | Prevention |
|---------|------|------------|
| Storing secrets in mise.toml (committed) | Credentials leaked to git history, public repos | Always use mise.local.toml for secrets, add to .chezmoiignore |
| Task scripts with hardcoded tokens | Secrets exposed in process lists, logs | Source from environment variables loaded via mise.local.toml |
| Not using redactions for sensitive env vars | Secrets printed in `mise env` output | Configure `redact = true` or use redaction patterns |
| Task scripts with `curl \| sh` without verification | Remote code execution, supply chain attacks | Always verify checksums, use pinned versions, review before executing |
| World-readable task files containing secrets | Any user on system can read credentials | Use `private_` prefix in chezmoi for sensitive task files |
| Task logs containing sensitive data | Credentials stored in shell history, log files | Sanitise output, use `MISE_QUIET=1`, avoid echoing secrets |

## UX Pitfalls

Common user experience mistakes in this domain.

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Tasks with no description | `mise tasks` output is unclear, users don't know what tasks do | Always include `#MISE description="Clear purpose"` in every task |
| Generic task names (`run`, `build`) | Name collisions with mise commands, unclear purpose | Use namespaced names (`dotfiles:apply`, `dev:build`) |
| No output during long-running tasks | Users think task is frozen, interrupt it | Print progress, use `echo "Step 1/3..."`, show what's happening |
| Cryptic error messages | Users can't self-diagnose, need support | Provide actionable errors with next steps: "ERROR: mise not found. Install with: brew install mise" |
| Tasks that modify system without confirmation | Destructive operations run accidentally | Use confirmations for destructive tasks, document with `--force` flags |
| Inconsistent task naming patterns | Hard to discover related tasks, unclear organisation | Use consistent prefixes: `dotfiles:*`, `dev:*`, `test:*` |

## "Looks Done But Isn't" Checklist

Things that appear complete but are missing critical pieces.

- [ ] **Task files:** Often missing executable permissions — verify with `ls -la ~/.mise/tasks/` shows `-rwxr-xr-x`
- [ ] **Cross-platform support:** Often missing platform detection in tasks — verify by testing on both macOS and Linux (or in Docker)
- [ ] **Error handling:** Often missing `set -e` or proper error checks — verify by introducing failures and ensuring graceful handling
- [ ] **Documentation:** Often missing task descriptions — verify `mise tasks` shows clear descriptions for all tasks
- [ ] **Secrets management:** Often storing secrets in committed files — verify `.gitignore` includes `*.local.toml` and no tokens in git history
- [ ] **Performance validation:** Often skipping shell startup benchmarking — verify with `hyperfine "zsh -i -c exit"` before and after changes
- [ ] **Working directory assumptions:** Often breaking when called from different directories — verify by running `cd /tmp && mise run <task>`
- [ ] **Dependency graph validation:** Often creating circular dependencies — verify with `mise tasks` (no errors) and testing parallel execution

## Recovery Strategies

When pitfalls occur despite prevention, how to recover.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Performance regression from mise activation | LOW | 1. Measure with `hyperfine`<br>2. Move tasks from mise.toml to file tasks<br>3. Configure mise to check only on chpwd<br>4. Re-measure and verify |
| Secrets committed to repository | HIGH | 1. Remove from current files<br>2. Add to mise.local.toml (gitignored)<br>3. Rotate all exposed credentials<br>4. Use `git filter-repo` to purge history<br>5. Force push (if private repo) or create new repo |
| Task file permissions broken | LOW | 1. Add `executable_` prefix in chezmoi source<br>2. Run `chezmoi apply`<br>3. Verify with `mise tasks` |
| Circular dependencies | MEDIUM | 1. Visualise with `mise tasks tree`<br>2. Identify cycles<br>3. Break cycles by using `wait_for` instead of `depends`<br>4. Flatten dependency hierarchy |
| Cross-platform failures | MEDIUM | 1. Identify platform-specific commands<br>2. Add platform detection (`if [[ "$OSTYPE" == "darwin"* ]]`)<br>3. Use portable shebangs (`#!/usr/bin/env bash`)<br>4. Test on target platform or in Docker |
| Chezmoi/mise overlap causing duplication | MEDIUM | 1. Document current state (what runs where)<br>2. Establish ownership boundaries<br>3. Remove duplication from one tool<br>4. Add validation to prevent future overlap |
| Task name collision with mise command | LOW | 1. Rename task to namespaced version (`dotfiles:install`)<br>2. Update all references in scripts/docs<br>3. Use `mise run` explicitly everywhere |
